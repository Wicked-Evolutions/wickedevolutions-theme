# v0.4 — Native-Core Minimal Plan

> Proposed next implementation phase for the Wicked Evolutions block theme.
> Scope discipline: **smallest change that resolves a real defect via the highest
> native WordPress/Gutenberg mechanism.** No speculative features, no new design system
> surface. Read-only analysis produced this plan; nothing here is implemented yet.
>
> **This is the narrow first safe slice — defect reconciliation, not the whole
> native-core conversion.** It closes one evidenced defect (the orphan landing-page
> enqueue) plus a trivial version-coherence fix. The full layer-by-layer audit and
> native-authority refactor — token model, variations, templates, block styles,
> runtime/plugin boundary, and editor QA — lives in
> [`v0.4-native-core-refactor-roadmap.md`](v0.4-native-core-refactor-roadmap.md).
> This plan is, at most, seed work toward that roadmap's phase 1 (authority spec)
> and phase 9 (Abilities verification); it does not settle the broader decisions.

---

## 1. Purpose

Close the one concrete, evidenced defect surfaced by the 2026-06-02 Abilities
inspection — an **enqueue rule that loads a stylesheet that does not exist** — and do
it through the native authority order rather than by reflexively shipping a CSS file.
Fold in a trivial, in-the-same-breath **version-coherence** fix while the file is open.
That is the entire phase. Everything else stays out (see §5).

The guiding question for the phase is *not* "what should we build next" but **"what is
already broken or incoherent, and what is the most native way to make it right."**

## 2. Current evidence

Gathered by reading the repo (no WordPress/MCP calls made for this plan):

- **Theme is genuinely native-first.** `theme.json` v3 carries the full design system
  (palette, fluid type scale, spacing scale, custom props); `styles/knowledge.json` is a
  style variation; `templates/` + `parts/` hold block markup; `patterns/*.php` are
  server-rendered composition. `assets/css/theme.css` opens with "Effects-only CSS.
  Layout via theme.json + editor settings" and largely honours that. The authority
  ladder in `AGENTS.md §1` is being respected — this plan must not erode it.
- **Orphan landing asset (the defect).** The inspection found one enqueue rule,
  `the-mirror-landing-page` → `assets/css/landing-page.css`, condition: template
  `page-landing`, "added by `ability`", with `file_exists=false`. Repo confirms:
  - No `assets/css/landing-page.css` in the theme.
  - No `templates/page-landing.html` in the theme.
  - No reference to `landing`, `page-landing`, or `the-mirror` anywhere in theme
    source (only in the two `docs/operations/` reports).
  The rule therefore lives in **WordPress option/mod state, not theme source**, and
  fires (if its template ever resolves) a request for a missing file.
- **Pre-existing dirty `assets/css/theme.css`.** `git diff` shows a ~35-line
  `/* ═══ FLUENTCART ═══ */` block mapping FluentCart's `--fct-*` variables onto theme
  presets. This is uncommitted worktree state and legitimate last-mile third-party
  theming. **Out of scope; preserve verbatim.**
- **Version drift.** `style.css` = `0.3.1`; `functions.php` docblock = `0.3.0`;
  `parts/header.html` hard-codes a `v0.3.0` badge; `theme.css` header says `v0.3.1`;
  live site reports `0.3.1`. Source of truth is `style.css` (`0.3.1`).
- **Already-logged gap.** `mcp_adapter_batch_execute` returned `Tool not found` for
  valid ability names (`abilities-gap-log.md`, Open). This is an **MCP-maintainer**
  item, not theme source — it stays logged, untouched by this phase.
- **Site-state observations, not theme work.** `footer` and `sidebar` menu locations
  unassigned. These are data operations for a later, separately-authorized Abilities
  session — not part of a theme-source phase.

## 3. Native authority diagnosis

Applying the `AGENTS.md §1` ladder to the orphan landing asset:

- The rule is an **ability-registered enqueue** — WordPress runtime state (tier 8),
  not theme code. A missing-file enqueue is a defect regardless of whether the file is
  ever requested, because the condition (`page-landing` template) is *also* absent, so
  the rule is doubly orphaned: it can neither match nor succeed.
- The only correct resolutions live at two ends of the ladder:
  1. **The Mirror landing genuinely needs distinct presentation** → climb the ladder:
     a `page-landing` template (tier 4) + a pattern (tier 5) + `theme.json`/style
     variation (tiers 2–3), dropping to a **committed** `assets/css/landing-page.css`
     (tier 9) *only* for true last-mile effects the higher tiers cannot express. The
     enqueue then either becomes theme-owned (`wp_enqueue_scripts`, conditional, like
     the existing `we-blog` pattern in `functions.php`) **or** the ability rule is
     repointed at a file that now exists.
  2. **No landing page exists / no bespoke styling is wanted** → the rule is pure
     cruft; **remove it via Abilities** (it cannot be removed by editing theme files —
     it isn't in them).
- **Do not** resolve this by dropping a stub `landing-page.css` into the theme to
  silence the missing-file condition. That inverts the ladder (CSS-first) and leaves an
  orphan template condition that still never matches. Investigate, then decide.

Version drift diagnosis: the badge is **static block markup** (`parts/header.html`), so
the native fix is simply correcting/removing the literal — there is no dynamic block or
binding obligation here, and inventing one would over-build.

## 4. Minimal next phase

**Primary — reconcile the orphan landing asset (decision-gated, no premature CSS):**

1. **Investigate (read-only Abilities).** Confirm via `mcp__wordpress__*`: the enqueue
   rule's provenance and exact stored shape; whether any `page-landing` page/template
   exists site-side; and that `landing-page.css` is genuinely absent everywhere. One
   read-only pass; no mutation. (Site is in read-only/inquiry mode — see §8.)
2. **Decide** between the two ladder-correct outcomes in §3.
3. **Execute the chosen branch:**
   - *Needs styling* → author `templates/page-landing.html` (+ pattern + any
     `theme.json` presets), and add `assets/css/landing-page.css` **only** for residual
     effects, enqueued the same conditional way `we-blog` is. Repoint or retire the
     ability rule so no environment references a missing file.
   - *Not needed* → remove the ability-registered enqueue rule via Abilities. If **no
     ability exists** to remove an enqueue rule → STOP, surface it, and log a gap in
     `abilities-gap-log.md`.

**Secondary — version coherence (only if it stays trivial):**

4. Make `0.3.1` consistent: bump the `functions.php` docblock and the hard-coded
   `v0.3.0` badge in `parts/header.html` to match `style.css`. Pure string edits to
   theme source; no logic change.

Net theme-source footprint: at most one small template/pattern + one optional
last-mile CSS file (only if §4 branch-1 is chosen), plus two one-line version edits.
Plausibly **zero** new theme files if the rule is simply retired.

## 5. Non-goals

- **No edits to `assets/css/theme.css`** — preserve the pre-existing FluentCart diff
  exactly; do not stage, revert, or extend it.
- **No TOC rework.** `patterns/toc.php`'s `the_content` regex ID-injection is deliberate
  (commit `dae4ba3`) and out of scope; not this phase's defect.
- **No menu-location assignment** (`footer`/`sidebar`) — separate, separately-authorized
  data operation.
- **No `mcp_adapter_batch_execute` fix** — MCP-maintainer concern; stays logged Open.
- **No new colors, fonts, spacing, variations, or multisite hardcoding.** No design
  system expansion.
- **No speculative `landing-page.css` stub** to silence the warning.

## 6. Acceptance criteria

- **No environment enqueues a non-existent stylesheet.** After the phase, either
  `landing-page.css` exists and is conditionally enqueued the native way, or the
  ability rule is gone — verified against live state via read-only Abilities.
- **The decision is recorded** (which branch, why, with the rule's provenance) in
  `docs/operations/` so the reconciliation is auditable.
- **If removal required an absent ability**, a gap row exists in
  `abilities-gap-log.md`; nothing was routed around silently.
- **`assets/css/theme.css` is byte-for-byte the pre-existing dirty version** — its
  FluentCart block untouched; `git status` still shows it modified for unrelated reasons.
- **Version strings are coherent** at `0.3.1` across `style.css`, `functions.php`,
  `parts/header.html` (if the secondary task is taken).
- **All WordPress operations went through Abilities**; no SSH/raw-REST fallback; the
  public-repo rules (§3 of `AGENTS.md`) held — no secrets or local config touched.
- **If branch-1 (styling) was chosen**, the new presentation is expressed at the
  highest applicable tier, with CSS used only for residual effects — reviewable against
  the authority ladder.

## 7. Claude / Hermes division of labor

  the two ladder-correct options for the user/Hermes to confirm before mutating.
- Author any template/pattern/`theme.json` change at the correct tier; write the

**Hermes (verification):**

- Confirm the enqueue ↔ file mismatch is actually reconciled (file exists *or* rule
  gone), not merely papered over.
- Confirm `assets/css/theme.css` FluentCart diff is preserved unmodified.
- Confirm no secrets / local config entered the tree; public-repo rules held.
- Sanity-check authority-ladder adherence (no CSS-first layout, no stub-to-silence).
- Confirm version coherence and that the decision record + any gap row exist.

## 8. Risks and guardrails

- **Ability-registered state ≠ theme source.** The enqueue rule cannot be fixed by
  editing files; adding `landing-page.css` without addressing the rule/template
  condition leaves the orphan in place. Treat removal/repointing as an **Abilities
  operation**; if blocked, STOP and log a gap — do not SSH or hand-edit options.
- **Read-only/inquiry mode is in force** on `wickedevolutions`. Any mutation step (rule
  removal, theme-mod change) requires the user to lift read-only first. The
  investigation step is safe as-is.
- **Doubly-orphaned condition.** Even a committed `landing-page.css` will not load
  unless a `page-landing` template *and* a matching page exist. Verify the full chain
  before declaring the styling branch "done."
- **Preserve worktree state.** The dirty `theme.css` and the untracked inspection doc
  are user/agent state; do not stage, commit, revert, or "tidy" them as part of this
  phase. Commits/pushes only on explicit instruction (`AGENTS.md §6`).
- **Public repo.** No `.env*`, `.mcp.json`, `wp-config.php`, keys, or dumps may enter
  any artifact (`AGENTS.md §3`).
- **Scope creep is the main risk.** The menu, TOC, batch-execute, and design-system
  temptations are all explicitly fenced off in §5; resist folding them in.
