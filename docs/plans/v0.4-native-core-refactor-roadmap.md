# v0.4+ — Native-Core Refactor Roadmap

> The broader roadmap for converting the Wicked Evolutions theme to a
> fully WordPress-native/Gutenberg-native core. This is a **roadmap, not an
> implementation** — it names the decisions, who owns each one, the phase order,
> and the acceptance bar. Nothing here is built yet.
>
> Read this against the canonical operating contract in [`AGENTS.md`](../../AGENTS.md);
> the authority ladder in `AGENTS.md §1` is the spine of every phase below.

---

## 1. North star

**The highest WordPress-native layer that can own a decision, owns it.** Every
visual or structural choice is pushed up the `AGENTS.md §1` ladder to the most
native mechanism that can express it — editor/core block supports, then
`theme.json`, then global styles/variations, then templates, then patterns and
block styles, then dynamic blocks, then theme PHP, then plugins/Abilities — and
only drops to **custom CSS/JS as the last mile**, for effects the higher tiers
genuinely cannot express.

CSS is not the design system. `theme.json` and global styles are the design
system; CSS is the residue after the native layers have spoken. When a decision
currently lives in CSS that a higher tier could own, that is a defect to migrate
upward, not a style to preserve.

## 2. Where the theme is today

The current theme is a **v0.3.x working prototype / source artifact**, not the
final architectural authority. It is already genuinely native-first — `theme.json`
v3 carries the palette, fluid type scale, spacing scale, and custom properties;
`styles/knowledge.json` is a style variation; `templates/` + `parts/` hold block
markup; `patterns/*.php` are server-rendered composition; `assets/css/theme.css`
declares itself "effects-only." That is a strong base.

But "native-first in practice" is not the same as "every decision provably lives
at its correct tier." v0.3.x was built to *work* and to *ship a product surface*,
not to *prove authority placement*. The roadmap's job is to walk the theme
layer-by-layer and make each decision's ownership explicit, inspectable, and
correct — promoting anything that drifted downward back up the ladder.

Treat v0.3.x as the source of truth for *intent and visual result*, and as the
*subject* of the audit — not as the binding precedent for *where* a decision
should live.

## 3. Strategy — hybrid, layer-by-layer, no blank slate

**Keep the repository. Branch and refactor one authority layer at a time.** There
is no blank-slate rewrite by default. A from-scratch rebuild throws away working,
shipped, install-aware behavior (see `CHANGELOG.md` 0.3.0) and the visual result
the brand already depends on, and it makes review impossible because everything
changes at once.

Instead:

- Each layer (or each decision class in §4) gets its own branch and its own PR.
- Each PR is small enough to review against the authority ladder and to diff for
  visual parity.
- A blank-slate rewrite is permitted **only** if a specific layer is proven
  unsalvageable, and only with explicit user sign-off for that layer — never as
  the default posture for the whole theme.

This keeps git history, keeps the theme installable at every step, and keeps each
authority decision auditable in isolation.

## 4. Decision ownership

Every decision class maps to exactly one owning native layer. The table is the
contract: when work touches a decision, it must be expressed at (or promoted to)
the owning layer, not solved one tier lower. Tier numbers track `AGENTS.md §1`.

| Decision class | Owning native layer (tier) | What it owns | What it must NOT do |
|---|---|---|---|
| **Design tokens & global settings** | `theme.json` (2) | Palette, fluid type scale, spacing scale, custom properties, layout/contentSize, enabled supports | Hard-code values in CSS that a preset could carry |
| **Style variations & global styles** | `styles/` global styles + variations (3) | Site-wide theming; named variations (e.g. `knowledge.json`); light/dark intent | Encode whole-site theming as CSS class toggles |
| **Templates & parts** | `templates/`, `parts/` (4) | Page/archive/single structure as block markup; header/footer/sidebar parts | Carry styling that `theme.json`/global styles should own; duplicate near-identical templates |
| **Patterns** | `patterns/*.php` (5) | Reusable composition; server-rendered assembly of blocks | Become a backdoor for layout CSS or for logic that belongs in a dynamic block |
| **Block styles & block stylesheets** | Block style variations + per-block stylesheets (5) | Named per-block style options; scoped block CSS registered the native way | Live as global selectors in `theme.css` when a registered block style fits |
| **Dynamic blocks & render callbacks** | Dynamic blocks / `render_callback` (6) | Output that must be computed at render (e.g. the server-rendered TOC, dynamic sidebar routing) | Be reimplemented as client-side JS when a render callback is correct |
| **Theme server logic** | Theme PHP `functions.php` (7) | Registration, enqueues, filters, install-aware capability model | Hold data/runtime operations that belong to Abilities |
| **Plugin / Abilities layer** | Plugins / Abilities MCP (8) | Live data/runtime operations; enqueue rules registered as abilities; capabilities beyond the theme | Be edited by hand-touching options; be bypassed via SSH/raw REST (`AGENTS.md §2`) |
| **CSS / JS enhancement** | `assets/` custom CSS/JS (9) | Last-mile visual effects; third-party theming bridges (e.g. FluentCart `--fct-*` mapping) | Own layout, tokens, or anything a higher tier can express |

The recurring question for every item of work is: *which row is this, and is it
currently sitting in the right row?* If it is sitting lower than its row, the work
is to promote it; if it is sitting in the right row, leave it.

## 5. Phases

Phases are ordered so that **authority decisions are made before cleanup**. You do
not tidy CSS or rename selectors until the layer that should own those decisions
has been settled. Each phase is one or more PRs (§3); each ends with the relevant
acceptance criteria in §7 met.

1. **Native authority spec.** Write down, per surface, which tier currently owns
   each decision and which tier *should*. Produces the audit map that every later
   phase consumes. No code changes — this is the "what is broken or misplaced"
   inventory, extending the read-only style of the minimal plan to the whole theme.
2. **Role-first token model.** Audit `theme.json` presets for role/intent naming
   (surface, text, accent, border — semantic roles) versus raw values, so global
   styles and variations can re-skin by role. Decide the token vocabulary before
   migrating any CSS into it.
3. **Global CSS decisions into `theme.json`.** Migrate values currently hard-coded
   in `assets/css/theme.css` that a preset or `theme.json` setting should own,
   moving them up to tier 2/3. CSS shrinks toward effects-only by *promotion*, not
   by hand-deletion.
4. **Light/dark / style-variation decision.** Decide whether dark-first plus any
   light mode is expressed as a style variation / global-styles mechanism (tier 3)
   rather than CSS class toggling. Settle the variation model before per-block work.
5. **Template cleanup.** Reconcile `templates/` and `parts/` to native structure:
   remove dead/duplicate templates, ensure structure is block markup and styling
   has been lifted to the owning tier. (CHANGELOG 0.3.0 already did one such pass on
   header parts — continue that discipline.)
6. **Component / block-style pass.** Convert recurring visual treatments into
   registered block style variations and properly scoped block stylesheets (tier 5),
   pulling per-block styling out of global `theme.css` selectors.
7. **Runtime behavior extraction.** Identify behavior that should be a dynamic block
   or render callback (tier 6) — e.g. the server-rendered TOC and context-aware
   sidebar routing — and confirm each computed-at-render decision lives there rather
   than in ad-hoc PHP or client JS.
8. **Theme vs site/product boundary.** Decide what belongs in the *base theme*
   versus what is *site/product-specific information architecture* (menus, routing,
   product surfaces). Site IA does not get absorbed into the base theme by default
   (§6). Draw the line explicitly and record it.
9. **Abilities verification harness.** Define the repeatable read-only Abilities
   pass that checks live/editor state against theme source — enqueue rules resolve
   to files that exist, registered abilities match expectations, no orphaned runtime
   state — so any authorized change can be verified before and after (`AGENTS.md §2`).
10. **Human editor QA.** Final pass confirming a human can open the WordPress Site
    Editor / Global Styles and **see and edit** the decisions this roadmap moved to
    native layers — i.e. the decisions are not just native in the files, they are
    native *to the editing experience*. Visual parity confirmed against v0.3.x
    unless a change was intentional.

Phases may overlap where independent (e.g. 6 and 7 touch different surfaces), but
the ordering constraint holds: **no layer's cleanup before that layer's authority
decision.**

## 6. Non-goals

- **No live deploy or production mutation.** This roadmap is repo work. Deploying,
  publishing, or mutating live WordPress state happens only on explicit, specific
  instruction (`AGENTS.md §4`).
- **No giant rewrite commit.** No single blank-slate or "convert everything" commit.
  Work is split into reviewable, layer-scoped PRs (§3).
- **No CSS cleanup before authority-layer decisions.** Renaming, deleting, or
  reorganizing CSS is downstream of deciding which tier owns the decision. CSS
  shrinks by promotion (phases 2–6), not by premature tidying.
- **No moving site/product IA into the base theme by default.** Menus, product
  routing, and site-specific information architecture stay out of the base theme
  unless phase 8 explicitly decides a given piece is genuinely theme-level.
- **No design-system expansion.** This is a *placement* refactor, not a new-features
  effort: no new colors, fonts, spacing scales, or surfaces introduced for their own
  sake.
- **No hand-touching Abilities/runtime state to "fix" the audit.** Runtime/enqueue
  state is reconciled through Abilities, not by editing options or SSH (`AGENTS.md §2`).

## 7. Acceptance criteria (for the roadmap as a whole)

- **Split into PRs.** The conversion ships as a sequence of small, layer-scoped PRs,
  each reviewable against the authority ladder — never one monolithic change.
- **Visual parity preserved unless intentionally changed.** Each PR is diffed for
  visual result against v0.3.x; any deviation is deliberate, called out, and signed
  off — not an accidental byproduct of moving a decision up a tier.
- **Editor-inspectable decisions.** After each phase, the decisions it moved to
  native layers can be **inspected and edited** in the WordPress Site Editor /
  Global Styles — proving the decision is native to the editing experience, not just
  to the source files.
- **Abilities-verified, before and after.** For any phase that touches authorized
  live/editor state, the §5.9 read-only Abilities harness verifies the live/editor
  state both before and after the change, and the result is recorded. No SSH or
  raw-REST fallback; public-repo security holds (`AGENTS.md §3`).
- **Auditable ownership.** At any point, the §4 table plus the phase records show,
  per decision class, that it sits at its owning tier — or that a logged, intentional
  exception explains why not.

## 8. Relationship to the minimal plan

[`docs/plans/v0.4-native-core-minimal-plan.md`](v0.4-native-core-minimal-plan.md)
is **only the narrow first safe slice** of this roadmap — a single, evidenced
defect reconciliation (the orphan landing-page enqueue) plus a trivial
version-coherence fix. It is *defect reconciliation*, not the full native-core
conversion and not the full audit remediation described here.

The minimal plan corresponds, at most, to early/seed work toward **phase 1**
(native authority spec) and **phase 9** (Abilities verification harness): it
demonstrates the read-only-investigate-then-decide discipline on one item. It does
**not** carry phases 2–8 or 10, and nothing in it should be read as having settled
the broader token model, variation model, template, block-style, runtime, or
theme/site-boundary decisions. Those remain open and are owned by this roadmap.

## 9. Version framing

The conversion is sequenced across minor versions so each version closes one band
of authority decisions:

- **v0.4 — native foundation.** Authority spec, token model, global CSS-into-
  `theme.json` migration, and the light/dark / style-variation decision (phases
  1–4). Establishes that the design system lives in `theme.json` + global styles.
- **v0.5 — component / pattern architecture.** Template cleanup and the
  component/block-style pass (phases 5–6). Establishes per-block and per-pattern
  ownership at tier 4–5.
- **v0.6 — dynamic / plugin boundary.** Runtime behavior extraction, the
  theme-vs-site/product boundary, the Abilities verification harness, and human
  editor QA (phases 7–10). Establishes where computed/runtime/data decisions live
  (tiers 6–8) and proves the whole thing is editor-native.

These are target bands, not a release schedule; each version still ships as
multiple PRs and only on explicit instruction (`AGENTS.md §4, §6`).
